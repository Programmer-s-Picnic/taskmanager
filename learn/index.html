The big picture: frontend and backend

Why GitHub Pages needs a separate Node.js server

GitHub Pages serves HTML, CSS and browser-side JavaScript. Node.js on GoDaddy runs JavaScript on the server. Your browser uses fetch() to send an HTTP request to the Node server, which replies with text or JSON.

The request journey: GitHub Pages → visitor's browser → HTTPS → GoDaddy Node.js → response back to browser.

We will begin with Hello World, verify the connection, and gradually build toward a full task manager.

Code to study and run
// In the browser console
console.log("Hello from GitHub Pages!");

// On GoDaddy, inside index.js
console.log("Hello from Node.js!");

Expected output

Browser console: Hello from GitHub Pages!
Server log: Hello from Node.js!
Try it: Identify which code runs in a browser and which code runs on GoDaddy.
Knowledge check: Can GitHub Pages run the Node.js server itself?

No. GitHub Pages hosts static files, not a persistent Node.js process.

Write Hello World in Node.js

Your first server using built-in JavaScript modules

Node.js lets JavaScript run outside a web browser. The built-in http module makes a server without Express or npm dependencies. req is the browser's request; res is the answer.

When someone opens the address, our server returns a plain-text Hello World message. The callback to listen() prints to the server's log, not to the browser.

Code to study and run
const http = require("node:http");
const PORT = process.env.PORT || 3000;

http.createServer((req, res) => {
  res.writeHead(200, {
    "Content-Type": "text/plain; charset=utf-8"
  });
  res.end("Hello World! Welcome to Programmer's Picnic.");
}).listen(PORT, () => {
  console.log("Server started on port " + PORT);
});

Expected output

Browser: Hello World! Welcome to Programmer's Picnic.
Terminal: Server started on port 3000
Try it: Change the greeting, restart your local Node server, and refresh the browser.
Knowledge check: Why do we use process.env.PORT?

GoDaddy may assign the port through an environment variable. The fallback 3000 is for local development.

Understand HTTP requests and responses

GET, URL paths, status codes, headers and bodies

The browser makes a GET request. Node replies with a status such as 200 (OK), a header such as Content-Type, and a response body. res.end() finishes the response.

Open Developer Tools → Network and observe the response headers. A route returning 404 means the requested path is not found.

Code to study and run
res.writeHead(200, {
  "Content-Type": "text/plain; charset=utf-8"
});
res.end("Hello World!");

Expected output

HTTP/1.1 200 OK
Content-Type: text/plain; charset=utf-8

Hello World!
Try it: What changes when you request /health rather than /?
Knowledge check: Does HTTP status 200 guarantee JSON content?

No. It means success; the body may be text, HTML, JSON or another type.

The package.json file

Build and start scripts for GoDaddy

GoDaddy Node.js Apps uses package.json to learn how to build and start your program. In our nodeuse repository, it is located in the repository root beside index.js.

The build script is a no-op because plain JavaScript does not require compilation. Node's HTTP module comes included, so no additional dependency installation is necessary.

Code to study and run
{
  "name": "taskmanager-hello-api",
  "version": "1.0.0",
  "private": true,
  "main": "index.js",
  "engines": { "node": "22.x" },
  "scripts": {
    "build": "echo build",
    "start": "node index.js",
    "test": "node --test"
  }
}

Expected output

npm run build → build
npm start → Server started on port 3000
Try it: Explain why index.js and package.json must both be included in the deployment.
Knowledge check: What does npm start run in this project?

The start script in package.json: node index.js.

Deploy nodeuse on GoDaddy

Use your cserver hosting dashboard and publish the server

  1. Open the GoDaddy hosting dashboard for cserver.learnwithchampak.live.
  2. Under Node.js Apps, click Add App.
  3. Choose GitHub as your source if offered, and select Programmer-s-Picnic/nodeuse. Alternatively, upload a ZIP with index.js and package.json at its root.
  4. Let GoDaddy build and start the app. Test the private preview first.
  5. Publish the app on an eligible hosting plan and public HTTPS domain. If it is mapped to cserver.learnwithchampak.live, the base URL will be https://cserver.learnwithchampak.live.
  6. Verify /, /health and /api/hello on the actual published address.
Important: the GoDaddy hosting dashboard domain is not automatically the URL of the Node app. Confirm the final published app mapping before treating cserver.learnwithchampak.live as the live API.
Code to study and run
# From your local nodeuse clone
npm run build
npm test
npm start

# Test locally
# http://localhost:3000/
# http://localhost:3000/health
# http://localhost:3000/api/hello

Expected output

/ → Hello World! Welcome to Programmer's Picnic.
/health → {"status":"ok","service":"taskmanager-hello-api"}
Try it: Deploy the backend and check the greeting in GoDaddy's preview.
Knowledge check: Is a private preview sufficient for a public GitHub Pages connection?

No. Publish your app on a public HTTPS URL, then use that exact address.

JSON and Node.js routes

Make the server answer different questions

Our nodeuse server responds to three endpoints: GET / returns plain text; GET /api/hello returns JSON; and GET /health reports basic service health. An unknown path returns HTTP 404.

JSON is a text format that JavaScript can turn into an object with response.json(). It is an effective way for the browser and server to exchange structured information.

Code to study and run
if (path === "/api/hello") {
  return sendJSON(res, 200, {
    connected: true,
    message: "Hello World! GitHub Pages is connected.",
    timestamp: new Date().toISOString()
  });
}

Expected output

{"connected":true,"message":"Hello World! GitHub Pages is connected.", ...}
Try it: Visit the three routes and compare their responses and Content-Type headers.
Knowledge check: What does GET /health report?

Basic service health. It does not authenticate users or store tasks.

Why CORS is necessary

Connecting two different web origins

Your GitHub Pages site has origin https://programmer-s-picnic.github.io; your GoDaddy backend has a different origin. Browsers restrict JavaScript from reading cross-origin responses unless the server permits access.

The nodeuse server sends Access-Control-Allow-Origin for your GitHub Pages origin and handles preflight OPTIONS requests. The origin does not include /taskmanager/.

CORS is not authentication. It controls browser access to responses. A production API storing private tasks still needs secure authentication and authorization.
Code to study and run
const allowed = "https://programmer-s-picnic.github.io";
if (req.headers.origin === allowed) {
  res.setHeader("Access-Control-Allow-Origin", allowed);
  res.setHeader("Vary", "Origin");
}
// See the complete handling in nodeuse/index.js.

Expected output

Access-Control-Allow-Origin: https://programmer-s-picnic.github.io
Try it: Inspect the CORS response header for /api/hello in Developer Tools.
Knowledge check: Does a CORS allowlist protect a private database?

No. CORS is not an access-control replacement. The server must check user credentials and permissions.

Fetch Hello World from GitHub Pages

Your first live frontend–backend connection

Now test the connection! The form below is already built into this site. It uses the suggested hosting address https://cserver.learnwithchampak.live, but treats it as unverified until your backend actually responds.

Once you publish nodeuse, click Connect & test. We request /api/hello and verify a recognizable JSON message. For a legacy plain-text server, the tester also tries /.

Code to study and run
const apiBase = "https://cserver.learnwithchampak.live";
const response = await fetch(apiBase + "/api/hello");

if (!response.ok) throw Error("HTTP " + response.status);

const data = await response.json();
console.log(data.message);

Expected output

Hello World! GitHub Pages is connected to Node.js on GoDaddy.
Try it: Use the live connection tester below and look for verified HTTP 200.
Knowledge check: Can a response from an unrelated website count as a successful NodeUse connection?

No. Our connection tester verifies the expected Hello World response, not merely HTTP 200.

Create tasks using HTML forms

Introduce browser state, validation and localStorage

Visit Task Entry, fill in a task name and save it. JavaScript handles the submit event, validates the task and stores it as a JSON object in browser localStorage.

The task remains after refreshing your own browser. At this stage tasks are not saved on GoDaddy; the Node app is still a read-only Hello World API.

Code to study and run
const items = JSON.parse(localStorage.getItem("demo-tasks") || "[]");
items.push({
  id: crypto.randomUUID(),
  name: "Finish Hello World",
  status: "Pending"
});
localStorage.setItem("demo-tasks", JSON.stringify(items));

Expected output

Task saved in this browser.
Try it: Add two tasks from Task Entry and open All Tasks to see them.
Knowledge check: Do localStorage tasks appear automatically on another computer?

No. LocalStorage belongs to the current browser and origin and is not a shared server database.

Practice CRUD: create, read, update, delete

The Task Manager frontend now supports creating, listing, editing, completing, deleting, searching and filtering tasks. These are the four foundational operations known as CRUD.

Task names are placed into the page with textContent, not unsafe HTML insertion. Try entering text containing angle brackets—your task should display as text instead of becoming HTML.

const item = items.find(t => t.id === chosenId);

Debugging and automated tests

Work like a professional developer

The nodeuse test file uses Node's built-in test runner. It checks the greeting, JSON route, health route, CORS response and an unknown path.

If the connection fails, diagnose whether the backend is deployed, whether the public URL is correct, whether HTTPS is configured, and whether CORS headers are present. Check GoDaddy runtime logs when the server does not start.

Code to study and run
git clone https://github.com/Programmer-s-Picnic/nodeuse.git
cd nodeuse
npm test
npm start

Expected output

TAP version 13
# Subtest: serves Hello World and CORS-enabled JSON
ok 1 ...
# pass 1
Try it: Run npm test locally, then intentionally break a response and observe what fails.
Knowledge check: Why test the app before publishing?

Tests can catch errors before the updated application reaches production visitors.

Your first task REST API design

Plan server-side create, read, update and delete

Once the greeting works, design the future REST endpoints for a real server-backed Task Manager. Example: GET /api/tasks, POST /api/tasks, PATCH /api/tasks/:id and DELETE /api/tasks/:id.

These are not implemented in nodeuse yet. A public task-writing API needs user authentication, authorization, server-side validation, safe database access and rate limits.

Code to study and run
// Future design only — not active in nodeuse
// GET    /api/tasks       — list your tasks
// POST   /api/tasks       — create task
// PATCH  /api/tasks/:id   — edit your task
// DELETE /api/tasks/:id   — delete your task

Expected output

Future goal: durable, authenticated tasks shared across devices.
Try it: Sketch a JSON task object and decide how the server checks task ownership.
Knowledge check: Should anyone on the internet be able to edit tasks without login?

No. Each operation should verify user identity and the user's right to access that task.

From Hello World to Infinity

Databases, security, real deployments and maintainability

Future milestones include Express routing, a MySQL or MSSQL database, parameterized SQL, task ownership, login and sessions, pagination, validation, backups, logging, performance testing, and automatic deployment.

The learning path remains incremental: first verify the connection, then add one protected task API, then durable storage, then security and polish. Node process memory is not reliable permanent storage, and putting database passwords in GitHub Pages would disclose them publicly.

When you finish all the introductory levels, keep using the same nodeuse backend repository for the later Node exercises and taskmanager for the browser interface. This separation closely resembles real client–server software.
Code to study and run
// Future server-side architecture:
// Browser frontend → authenticated HTTPS API
// → input validation → authorized task logic
// → parameterized SQL → durable database
// → logging and backups

Expected output

Goal: a secure, durable, multi-device Task Manager.
Try it: Draw your ideal task API, database tables and user permission rules.
Knowledge check: Does CORS alone make a public task API secure?

No. Authentication, authorization, validation and server-side security controls are essential.
